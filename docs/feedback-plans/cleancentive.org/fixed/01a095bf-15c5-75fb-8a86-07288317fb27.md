## Analysis
Every detected-item edit (`PATCH /spots/:spotId/items/:itemId` → `SpotService.updateDetectedItem`)
and every steward "confirm detection" (`POST /spots/:spotId/confirm-detection`) ended with two
un-awaited calls:

```ts
// Clear identity map so subsequent queries fetch fresh data with updated relations
this.spotRepository.manager.clear(Spot);
this.detectedItemRepository.manager.clear(DetectedItem);
```

TypeORM's `EntityManager.clear(Entity)` is `TRUNCATE TABLE`, not a cache reset; TypeORM has no
identity map. The pair dates from c27314d (2026-03-29) and was copied into `confirmDetection` in
bbd7e96 (2026-09-11).

Prod backend logs (read-only inspection, 2026-09-12): six crashes today, each

```
error: cannot truncate a table referenced in a foreign key constraint
      query: "TRUNCATE TABLE \"spots\""
     detail: "Table \"detected_items\" references \"spots\"."
error: script "start" exited with code 1
```

each seconds after a `New label created` line from the reporter (13:10:5x, a 13:11 restart loop,
18:20, 18:25 UTC). Container `RestartCount=6`. Bun exits on the unhandled rejection, Docker
restarts the container (~4 s), Caddy answers 502 for the in-flight request and anything else in
that window. The feedback was filed at 13:12:03 UTC, one minute into the restart loop.

Data was not lost: `spots` 2218 rows, `detected_items` 2655, `n_tup_del` small. That is only
because `detected_items` → `spots` and `detected_item_edits` → `detected_items` foreign keys
blocked both truncates. This was a data-loss near miss on the two core tables.

Contributing factors:
- The frontend never checked `res.ok` on item/spot mutations, so the UI claimed success.
- The spec stubbed `manager.clear` as a no-op, so tests could not see the TRUNCATE.
- Bun's raw rejection dump has no logger prefix; the cause was only findable by grepping the SQL.

Ruled out: Redis `KEYS` in the insights cache subscriber, missing `'error'` listeners on
ioredis/BullMQ (both log rather than throw), deploy restart (promoted 10:47 UTC), OOM, payload size.

## Implementation Plan
1. Remove the four `manager.clear(...)` lines from `updateDetectedItem` and `confirmDetection`.
   Freshness is already handled inside the transaction (stale eager relation nulled) and the
   controller returns FK ids from the saved entity.
2. Spec: stub `manager.clear` to throw; add `updateDetectedItem` tests.
3. ESLint `no-restricted-syntax` in `backend/.eslintrc.cjs` banning `.clear()` and `.clear(Entity)`
   call shapes; rewrite the one intentional `teamCollectionRepository.clear()` as `delete({})`.
4. `main.ts`: `unhandledRejection` / `uncaughtException` handlers that log via Nest `Logger`
   then exit 1 (fail-fast kept, cause visible).
5. Frontend: shared `throwIfNotOk` helper; ItemEditor, SpotEditor, SpotDetail check the response
   and show an inline error instead of calling the success callback.
6. Acknowledge upstream; close via `Fix 01a095bf-15c5-75fb-8a86-07288317fb27` commit trailer;
   deploy with promoto.
