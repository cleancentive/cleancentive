## Analysis

**Root cause.** `frontend/src/lib/imageMetadata.ts` `extractImageMetadata()` throws in four situations and every throw discards the photo with no recovery path. The one hit here is line 48-50:

> `'This photo has no GPS metadata. Enable Location in your camera app and try again.'`

On iOS, Safari transcodes HEIC→JPEG and **strips the GPS block** when a photo is picked via *Photo Library* in an `<input type="file">`; picking via *Browse*/Files preserves it. The photo genuinely has GPS on the device, the bytes handed to the web app do not, and the message blames the user's camera settings for something Safari did — which is exactly the loop the reporter described: he checked his settings, confirmed the GPS tag, and had nowhere to go.

**Affected area.** `frontend/src/lib/imageMetadata.ts`, and both of its call sites — `CapturePanel.queueImportedFile` (single file) and `BatchImportDialog` (batch, the more common iOS path at 96 of 109 iOS import events).

**Contributing findings:**

1. **No failure telemetry anywhere.** Only five event names exist (`spot-logged`, `team-joined`, `cleanup-created`, `cleanup-joined`, `sign-in-completed`), all success events. Every import failure in the app's history is unrecorded — which is why this surfaced only as a user complaint.
2. **Second false-rejection path:** `image/png` is in neither `SUPPORTED_MIME_TYPES` nor `SUPPORTED_EXTENSIONS`, so a screenshot is rejected as "format not supported" before exifr ever runs.
3. **Third silent-drop path:** `BatchImportDialog.importGroup`/`importAll` `continue` past any photo with `latitude == null`; those photos are counted in the group header, then never queued, and `importedCount` under-reports with no explanation.
4. **Misleading copy:** `map.json` `skipped_one/_other` assert "(no GPS data)" for every skip reason, including unsupported-format and corrupt-file.
5. `createThumbnailFromBlob` throwing (HEIC on non-Safari) also destroys a photo whose GPS *was* read fine.

## Implementation Plan

Full plan: `~/.claude/plans/analyse-https-cleancentive-org-steward-f-tingly-lantern.md`.

Scope agreed: import path + telemetry. Server-side hardening (MIME allowlist on `POST /spots`, `getFileExtension` storing HEIC/AVIF under `.jpg` keys) deliberately out of scope.

1. **`imageMetadata.ts` → result type, never throws.** Discriminated union `{ status: 'located', latitude, longitude } | { status: 'unlocated', reason }` with `LocationMissingReason = 'unsupported-format' | 'unreadable' | 'no-gps' | 'invalid-gps'`. Run `exifr.parse` unconditionally (drops the allow-list gate, fixing PNG); read `capturedAt`/`accuracyMeters` *before* coordinates so a GPS-less photo keeps its timestamp. Keep the exported name so `tsc` names both call sites.
2. **`imageMetadata.spec.ts` (new, written first)** using `bun:test`, with `gps-tagged.jpg` / `gps-stripped.jpg` fixtures under `src/lib/__fixtures__/`.
3. **i18n** — reason-specific strings incl. an iPhone Files/Browse hint shown only for `reason === 'no-gps'`; reword the `skipped` "(no GPS data)" claim. en + de + fr (locales.spec.ts enforces key parity).
4. **`CapturePanel.tsx`** — on `unlocated`, keep the photo in new `pendingImport` state (isolated from the session-wide `manualLocation`, which the camera path reads) and offer **Place on map** via the existing `ManualLocationDialog` / **Discard**.
5. **Tolerant thumbnails** — a `createThumbnailFromBlob` failure no longer destroys the photo; `thumbnailBlob: null` is already legal end to end.
6. **`BatchImportDialog.tsx`** — stop discarding unlocated photos; one `batchPin` for the whole batch; shared `queueGroupItems` helper reporting `unplaced` instead of silently continuing.
7. **Telemetry** — `spot-import-failed { reason, source }` and `spot-import-recovered { method, source }`.

Offline outbox stays at `DB_VERSION = 4` — nothing is queued until it has coordinates, and `openDatabase()` has no `onblocked` handler, so a version bump is actively dangerous.
