## Original Feedback

## Error Context
None

## Conversation Thread

## Analysis

Most of this request was **already shipped** before the feedback arrived. The inventory:

| Capability | State before this change |
|---|---|
| Create a whole series in one action | ✅ `DateForm` "Repeat" toggle → `generateRecurringDates()` → `POST /cleanups/:id/dates/bulk` |
| Weekly / biweekly / monthly / quarterly / yearly | ✅ `Frequency` union in `frontend/src/lib/cleanupDates.ts` |
| Preview before committing | ✅ live `repeatPreview` list under the repeat controls |
| Series stays identifiable | ✅ shared `recurrence_id`, distinct hue per series via `recurrenceColor()` |
| Select / delete a whole series | ✅ `useCleanupSelection` groups by `recurrence_id` |
| **Different meeting points per occurrence** | ✅ every `CleanupDate` already carries its own `latitude`/`longitude`/`location_name`, editable per date |

So "different meeting points possible" needed no work at all — editing one occurrence's
location has never disturbed the rest of the series.

The one genuine gap: the series length could only be expressed as a **fixed occurrence
count** (2–52). A village organising "every second Saturday until the end of the season"
had to count the Saturdays by hand.

### A discarded first attempt

An earlier attempt at this feedback built a parallel server-side recurrence system — a
`cleanup_recurrences` table, `CleanupRecurrenceService`, seven REST endpoints, a migration,
and a pattern-editor modal. It was reverted unshipped, because:

- It never ran. A mis-copied `ISO_WITH_OFFSET` regex in the new controller (missing the
  colon before the seconds group) rejected every `toISOString()` value, so
  `POST /recurrences/:id/generate` returned 400 on every call.
- It stamped `recurrence_id: null` on the dates it generated, so its output was invisible
  to the existing series badge and to bulk select/delete.
- `interval` was stored, validated and exposed in the UI but never applied — "every 2
  weeks" silently meant every week.
- Generated dates were fixed at 00:00–02:00 server-local and inherited coordinates
  `{0, 0}` when the cleanup had no prior date.
- It bypassed `assertDateWindow`, `assertCoordinates` and `ensureCleanupNotArchived`, and
  its `regenerateDates` deleted dates without first clearing `users.active_cleanup_date_id`.

Maintaining a second recurrence concept alongside `recurrence_id` was not worth it for the
one feature actually missing. The change below extends what already works instead.

## What shipped

An "Ends" mode on the existing repeat controls: **after N occurrences** (the previous
behaviour, unchanged and still the default) or **on date**.

- `frontend/src/lib/cleanupDates.ts` — added `generateRecurringDatesUntil()`,
  `endOfLocalDay()` and the `MAX_OCCURRENCES` cap (52). `endOfLocalDay()` exists because an
  `<input type="date">` value is a bare calendar day: "until 31 Aug" must mean the end of
  31 Aug in the organiser's timezone, not UTC midnight, or the last occurrence silently
  drops out. `MAX_OCCURRENCES` bounds the open-ended mode so a date far in the future can
  never write an unbounded series.
- `frontend/src/hooks/useCleanupDateForm.ts` — added `repeatMode: 'count' | 'until'` and
  `repeatUntil`; `repeatPreview` picks the matching generator. The existing 2–52 clamp now
  reads from `MAX_OCCURRENCES`.
- `frontend/src/components/cleanup/DateForm.tsx` — an "Ends" `<select>`, with the
  occurrence-count input and the until-date input swapping behind it. The until-date input
  is floored at the start date. Preview and the `(N)` submit-button count work unchanged in
  both modes.
- `frontend/src/components/CleanupDetail.tsx` — the bulk-create guard was
  `form.repeatEnabled && form.repeatCount > 1`, which is blind to until-mode. Now
  `form.repeatEnabled && form.repeatPreview.length > 1`, matching the submit label's logic.
- `frontend/src/lib/cleanupDates.spec.ts` — 9 new cases covering inclusive until-day
  boundaries, an until date before the start, unparseable input, and the cap. Timezone-safe:
  starts are built from local parts so assertions hold anywhere.
- `frontend/src/i18n/locales/{en,de,fr}/cleanups.json` — `dateForm.endsLabel`,
  `dateForm.ends.{afterCount,onDate}`, `dateForm.untilLabel`. All three locales, so
  `locales.spec.ts` parity holds.

No backend change, no migration, no new entity. Series created in until-mode flow through
the same `POST /cleanups/:id/dates/bulk` endpoint and therefore keep their `recurrence_id`,
their colour badge, and their bulk select/delete — and each occurrence keeps its own
editable meeting point.
