## Original Feedback
> The page asks for user's location before anything is loaded. Without any details. Without any explanation on what are we looking at. At best paranoid people will hit "deny" and explore and allow later or (quite likely) leave immediately or not even know how to re-allow location sharing.
>
> Suggestion: There should be an active prompt (get my location & upload?) before user's location is asked for.

## Analysis

The native geolocation permission dialog fired on page load with no in-app context. Root cause: [locationStore.ts](frontend/src/stores/locationStore.ts) started `navigator.geolocation.watchPosition()` as a **module-level side effect** — it ran the instant the store was imported (when `CapturePanel` mounts on `/`). The only gate blocked the already-`denied` state, so a fresh (`prompt`) state triggered the browser dialog immediately.

Reporter also noted: on `cleancentive.local` the grant persists, on `cleancentive.org` it re-prompts after each browser restart. The frontend code is identical on both — geolocation permission persistence is a browser-side, per-origin decision (an "allow this time" grant, or a "clear site data on close" rule on the prod origin). Code can't force a browser to remember a grant.

Per steward direction, this was widened from a capture-panel patch into an **app-wide consistent location concept**. Inventory found four geolocation entry points, two of which fired without a user gesture:

| Surface | API | Trigger (before) |
|---|---|---|
| `locationStore` watch | `watchPosition` | auto on app load |
| `LocationPicker` auto-center | `getCurrentPosition` on mount | auto, silent |
| `LocationPicker` 📍 button | `getCurrentPosition` | user click |
| `MapPage` "Find my location" | MapLibre `GeolocateControl` | user click |

**Severity:** medium — quality-of-life / trust suggestion, no broken functionality.

## Implementation Plan

Unifying rule: *no native prompt without an explicit in-app gesture; once the browser reports `granted`, every surface uses location silently.* Consent state lives in one place (`locationStore`). Map keeps MapLibre's native control (decision: "keep native, share consent").

1. **`locationStore`** — added a `consent: 'unknown' | 'needed' | 'granted' | 'denied' | 'unsupported'` field (superseding `permissionDenied`/`notSupported`) and a `requestLocation()` action that persists a `localStorage` opt-in (`cc-geo-consent`) and starts the shared watch. Replaced the module-level auto-start with a non-prompting init: `permissions.query` → `granted` auto-starts silently; `prompt` settles on `needed` (no watch); `denied`/no-API set the matching state. Browsers without the Permissions API trust the persisted opt-in. A successful fix marks `consent: 'granted'`.
2. **`CapturePanel`** — when `consent === 'needed'`, renders an inline, non-blocking "Enable location" card (why + Enable button → `requestLocation()` + manual fallback). `denied`/`unsupported` show a friendly message; manual location still works.
3. **`LocationPicker`** — removed the silent auto-`getCurrentPosition()` on mount; centers from the shared store's last fix when available, else default view. The explicit 📍 button now persists consent via `requestLocation()` and surfaces a friendly message instead of failing silently.
4. **`MapPage`** — unchanged; the native `GeolocateControl` is an explicit gesture and inherits the unified consent.
5. **i18n** — shared `location.*` copy added to `common.json` (en/de/fr).

### Verified (dev, cleancentive.local)
- `granted` → watch resumes silently, no card, no prompt (±46 m pill).
- `prompt`/`needed` → consent card renders (DE copy confirmed), no native prompt fired.
- `bun run tsc` passes; 0 console errors.

## Reopen postmortem (2026-08-25)

`git rev-list --left-right --count origin/main...main` returned `0 1`: the entire fix was
one unpushed commit. Any triage that reads `prod_status` will keep reopening an item in
this state, correctly — the user-visible behaviour really had not changed.

The dev-only verification recorded above was re-run against current `main`, and this time
pinned down as an automated regression test rather than a manual pass:

**[frontend/e2e/location-consent.spec.ts](frontend/e2e/location-consent.spec.ts)** — 3 passing tests.
They instrument `navigator.geolocation` and assert on *when* the app reaches for it, which
is the part that regressed:

| State | Assertion | Result |
|---|---|---|
| Fresh visitor (permission `prompt`, no opt-in) | zero `getCurrentPosition`/`watchPosition` calls on load; `.location-consent` card visible instead | pass |
| Explicit gesture | zero calls before clicking Enable, at least one after | pass |
| Returning visitor (permission `granted`) | `watchPosition` starts silently, no card | pass |

The original bug — `watchPosition()` as a module-level side effect — would fail the first
two outright.
